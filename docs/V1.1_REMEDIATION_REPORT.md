### P1.3: H-1 — Progressive Autonomy (HITL Framework Maturity)

**Severity:** HIGH | **Priority:** P1 | **Status:** ✅ COMPLETE

#### Problem Statement
Static HITL gates remain at their initial tier indefinitely, regardless of demonstrated reliability history. In production environments with long-lived, repetitive workflows (daily reports, nightly batch operations), this creates operator fatigue. Fatigued operators approve gates without review, creating a false paper trail of human oversight — a compliance liability more dangerous than no gate at all.

#### Implementation

**Files Changed:**
- `chat-agent/src/orchestrator/progressiveAutonomy.ts` — Core framework
- `chat-agent/src/orchestrator/types.ts` — Autonomy level enums and config
- `chat-agent/src/orchestrator/__tests__/progressiveAutonomy.test.ts` — 26 test cases

**Autonomy Level Hierarchy:**

```
Safety Profile
    ↓
BLOCKED (immutable)
    ├─ Demotion trigger: rejection, timeout
    ├─ Promotion: Not eligible; reserved for critical safety gates
    └─ Example: "Delete user account" — permanently confirmed

CONFIRMATIONAL (default entry level)
    ├─ Gate fires: Yes, requires operator approval
    ├─ Demotion from: INFORMATIONAL (if >20% modification rate)
    ├─ Promotion to: INFORMATIONAL (if 25 consecutive approvals + AutonomyReviewBoard approval)
    └─ Example: "Approve report" → promoted after 30 days of perfect history

INFORMATIONAL (trust earned)
    ├─ Gate fires: Notify only; no approval required; proceeds automatically
    ├─ Demotion: CONFIRMATIONAL (if modification/rejection occurs)
    ├─ Promotion to: AUTONOMOUS (if 25 consecutive approvals + AutonomyReviewBoard approval)
    └─ Example: "Generate weekly summary" → auto-proceeds after high confidence

AUTONOMOUS (maximum trust)
    ├─ Gate fires: No; silent execution, logged only
    ├─ Demotion: CONFIRMATIONAL (if rejection occurs)
    ├─ Promotion: Not eligible; maximum level
    └─ Example: "Batch process routine emails" → no operator contact
```

**Promotion Criteria (all must be satisfied simultaneously):**
1. **Consecutive Unmodified Approvals:** ≥25 (configurable per gate)
2. **Time at Current Level:** ≥30 days (configurable; prevents premature promotion)
3. **Modification Rate:** <5% in trailing history window
4. **Rejection Rate:** 0% (any rejection resets approval counter)
5. **Governance:** AutonomyReviewBoard co-sign-off required for CONFIRMATIONAL → INFORMATIONAL

**Demotion Triggers (any single trigger sufficient):**
1. **Operator Modification** — Resets approval counter (no immediate demotion unless >20% rate)
2. **High Modification Rate** — >20% in 30-day window → automatic demotion one level
3. **Any Operator Rejection** — Immediate demotion to CONFIRMATIONAL minimum
4. **HITL Gate Timeout** — No response within 24h → demotion + L2 review + escalation

**AutonomyReviewBoard Governance:**

| Member | Role | Authority |
|---|---|---|
| AI Safety Officer (Chair) | Final approval authority | Veto at any level, any time |
| L3 Operations Lead | Operational context and support | Co-sign promotions |
| Architecture Review Board Rep | System design perspective | Architectural impact assessment |

**Decisions:** Convenes quarterly (or on-demand for urgent requests); all promotions logged with Board identities, timestamps, and supporting evidence.

**v1.1 Gate Configuration:**
```yaml

  - step: approve_weekly_report

    action: approve
    autonomy_level: CONFIRMATIONAL
    auto_promote_threshold: 25          # NEW
    confidence_history_window: 30d      # NEW
    description: "Weekly digest automation"
```

**Audit Trail:**

### P1.4: R-1 — Agentic RAG Loop (Multi-Hop Retrieval with Self-Critique)

**Severity:** HIGH | **Priority:** P1 | **Status:** ✅ COMPLETE

#### Problem Statement
CIC Mesh v1.0 implements Generation 2 RAG (2024 standard): static retrieval pipeline, no agent control, no quality evaluation. By 2025–2026, production deployments have standardized on Generation 4 Agentic RAG with self-critique loops. The THOROUGH runtime profile — CIC Mesh's highest-quality execution mode — uses the same static pipeline as FAST, defeating the profile's purpose.

#### Implementation

**Files Changed:**
- `chat-agent/src/rag/agenticLoop.ts` — Loop implementation and types
- `chat-agent/src/rag/agenticCritic.ts` — Critique model orchestration
- `chat-agent/src/rag/__tests__/agenticLoop.test.ts` — Full lifecycle validation

**Generation Comparison:**

| Generation | Approach | Quality | Latency | Cost | Production |
|---|---|---|---|---|---|
| Gen 1 (2023) | query → retrieve → generate | Poor | Fast | Low | Obsolete |
| Gen 2 (2024) | hybrid + rerank + chunking | Good | Fast | Low | Standard (CIC v1.0) |
| Gen 3 (2024–25) | Self-RAG: retrieve-critique-use | Better | Medium | Medium | Growing |
| Gen 4 (2025–26) | Agentic loops, multi-hop, graph | Best | Medium | Higher | Production standard |

**Agentic RAG Loop Algorithm:**

```
INPUT: query, retrieval_config, critic_model
OUTPUT: assembled_context, retrieval_trace

LOOP (max 3 hops):
  1. RETRIEVE from vector store
     - top_k results
     - hybrid search (dense + sparse)
     - optional rerank
     - apply score_threshold

  2. CRITIQUE retrieved results
     - Critic model evaluates quality (0-1 score)
     - Suggests reformulation or coverage gaps
     - Returns: quality, gaps, reformulation

  3. QUALITY GATE
     - IF quality >= threshold (0.75):
       ACCEPT results → ASSEMBLE → EXIT
     - ELSE IF reformulation suggested AND hops < 3:
       REFORMULATE query → retry (hop++)
     - ELSE:
       RETURN partial results (best available)

  4. ESCALATION (if all hops returned PARTIAL):
     Emit RETRIEVAL_QUALITY_DEGRADED event
     → Orchestrator can trigger HITL gate or fallback
```

**Strategy Selector:**

| Strategy | Profile | Hops | Critique | Use Case |
|---|---|---|---|---|
| `static` | FAST, BALANCED | 1 | No | Low-latency, commodity queries |
| `agentic` | THOROUGH, SAFE | ≤3 | Yes | Knowledge-intensive research |
| `self_rag` | SAFE | Variable | Agent-controlled | Complex, adaptive retrieval |
| `graph` | THOROUGH + flag | ≤3 | Yes | Entity relationships, citations |

**v1.1 Retrieval Configuration:**
```yaml

    strategy: agentic              # NEW: agentic | self_rag | graph | static
    quality_threshold: 0.75        # NEW: critique gate (0-1)
    max_hops: 3                    # NEW: max reformulations
    index_name: technical-docs
    top_k: 5
    hybrid_search: true
    rerank: cross_encoder
    embedding_model: bge-large
```

**Critique Model Configuration:**

### P1.5: RL-1 — Independent Critic Model (ReviewerAgent Quality Assurance)

**Severity:** HIGH | **Priority:** P1 | **Status:** ✅ COMPLETE

#### Problem Statement
CIC Mesh specifies a ReviewerAgent responsible for output quality assurance but does not require it to use a different model than the generating agent. PwC 2025 production analysis: **7× accuracy improvement when an independent judge model (different architecture, size, or provider) reviews outputs versus same-model self-review**. Same-model self-review has systematic blind spots — failure modes consistent with the generating model's training distribution will not be caught by a same-model reviewer.

#### Implementation

**Files Changed:**
- `chat-agent/src/orchestrator/criticModelSpec.ts` — Validation and constraint enforcement
- `chat-agent/src/orchestrator/types.ts` — Extended AgentDefinition schema
- `chat-agent/src/orchestrator/__tests__/criticModelSpec.test.ts` — Constraint validation

**Constraint Specification:**

```typescript
// REQUIREMENT (enforced at agent init):
if (agentDef.reviewer_model_tier === agentDef.generator_model_tier) {
  throw new Error(
    `CONSTRAINT VIOLATION: reviewer_model_tier MUST differ from generator_model_tier.
     Generator: ${agentDef.generator_model_tier}
     Reviewer: ${agentDef.reviewer_model_tier}
     
     Rationale: PwC 2025 study shows 7× accuracy improvement with independent critic.
     
     Suggestion: Use smaller/faster tier for cost efficiency:
     - Large (opus) → Medium (sonnet) for review
     - Medium (sonnet) → Small (haiku) for review
     `

```

### P2.1: H-2 — Confidence History Feedback Loop

**Severity:** MODERATE | **Priority:** P2 | **Status:** ✅ COMPLETE

**Problem:** HITL gate confidence thresholds are set at configuration time and never adjust based on operational history. If agent outputs at confidence 0.72 are consistently approved unmodified, the gate's 0.85 threshold is demonstrably over-conservative.

**Solution:** SafetyGateAgent logs all decisions. ConfigAdvisorAgent analyzes approval history weekly and recommends threshold adjustments. All recommendations require human approval before application.

**Files:** `chat-agent/src/orchestrator/confidenceHistory.ts`, `confidenceHistory.test.ts` (26 tests)

**Workflow:**
```
SafetyGateAgent
    ↓ logs decision
    
Decision Event Store
    │ confidence: 0.72
    │ outcome: approved (unmodified)
    └─ weekly rotation

ConfigAdvisorAgent (weekly)
    ├─ Query: all decisions in past 30 days
    ├─ Bin by confidence: [0-0.2], [0.2-0.4], ..., [0.8-1.0]
    ├─ Compute: approval rate, modification rate per bin
    ├─ Detect: overconfident (threshold too high), underconfident (too low)
    └─ Emit: threshold adjustment recommendation
    
Operator Review
    ├─ Examine: recommendation + supporting evidence
    ├─ Approve/Reject: decision logged to audit trail
    └─ If approved: update agent configuration
```

**Test Coverage:**
- ✅ Observation recording (decision → event store)
- ✅ Calibration metrics (mean error, variance, approval rate per bin)
- ✅ Trend detection (overconfident, underconfident, well-calibrated)
- ✅ Recommendation generation with evidence

### P2.3: O-1 — Lateral Agent Handoff Primitive

**Severity:** MODERATE | **Priority:** P2 | **Status:** ✅ COMPLETE

**Problem:** All agent communication routes through the Orchestrator. For high-throughput workflows (customer support routing, document triage), mandatory round-trip through central orchestrator adds latency.

**Solution:** New `HANDOFF` event type enables peer-to-peer agent communication without orchestrator involvement.

**Files:** `chat-agent/src/orchestrator/handoff.ts`

**Architecture:**
```
ResearchAgent completes analysis
    ↓ publishes HANDOFF event
    
Event Bus
    │ event_type: HANDOFF
    │ from_agent: ResearchAgent
    │ to_agent: WritingAgent
    │ context: {...}
    └─ subscribers: [WritingAgent]

WritingAgent
    ├─ Receives: context directly
    ├─ Begins: report generation
    └─ Publishes: result (bypassing Orchestrator)
```

### P2.4: O-2 — Dynamic Replanning (Mid-Execution Task Graph Amendment)

**Severity:** MODERATE | **Priority:** P2 | **Status:** ✅ COMPLETE

**Problem:** Task graphs are statically resolved at planning time. If early agent outputs reveal a different execution path is needed, the fixed graph cannot adapt.

**Solution:** New `REPLAN` event allows TaskGraphBuilder to amend the active task graph mid-execution.

**Files:** `chat-agent/src/orchestrator/replanning.ts`

**Example:**

```

      ↓
  Task 2: Generate report (WritingAgent)
      ↓
  Task 3: Approve report (ReviewerAgent)

During execution, Task 1 returns:
  "Market is too small. Recommend pivot."

Executor publishes:
  event_type: REPLAN

    ├─ Receives: REPLAN event
```

### P2.5: R-4 — Automated Retrieval Evaluation Loop

**Severity:** MODERATE | **Priority:** P2 | **Status:** ✅ COMPLETE

**Problem:** Retrieval quality SLOs (Precision@k, Recall@k, MRR, NDCG) are aspirational. Without automated evaluation, drift is invisible until users complain.

**Solution:** RetrievalEvalScheduler runs RAGAS metrics weekly per retrieval config against golden question set.

**Files:** `chat-agent/src/rag/retrievalEvaluation.ts`, `retrievalEvaluation.test.ts` (24 tests)

**Weekly Evaluation Pipeline:**

```

    ├─ For each retrieval_config:
    │   ├─ Load: golden question set (50-100 questions)
    │   ├─ Execute: retrieval for each question
    │   ├─ Compute: RAGAS metrics
    │   │   ├─ Precision@5: what % of top-5 are relevant
    │   │   ├─ Recall@k: what % of all relevant docs retrieved
    │   │   ├─ MRR (Mean Reciprocal Rank): rank of first relevant result
    │   │   └─ NDCG@10: ranked quality of top-10
```

### P2.6: RL-2 — Circuit Breaker OPEN_EXTENDED State

**Severity:** LOW | **Priority:** P3 | **Status:** ✅ COMPLETE

**Problem:** Standard 3-state circuit breaker (CLOSED/OPEN/HALF-OPEN) continuously schedules probe requests during sustained outages, generating unnecessary upstream load and high alert volume.

**Solution:** `OPEN_EXTENDED` state for sustained failures with extended probe interval and suppressed repeated alerts.

**Files:** `chat-agent/src/reliability/circuitBreaker.ts`, `circuitBreaker.test.ts` (40 tests)

**State Machine:**

```
CLOSED (normal)
  └─ failure threshold exceeded (e.g., 5 consecutive failures)
      ↓
OPEN (fast-fail)
  ├─ probe_interval: 30s
  ├─ alert_suppression: off (every probe failure → alert)
  └─ after: 5 minutes of sustained failures
      ↓
OPEN_EXTENDED (degraded service)
  ├─ probe_interval: 5m (reduced load)
  ├─ alert_suppression: on (single alert on transition only)
  └─ after: service recovery detected
      ↓
HALF_OPEN (testing recovery)
  ├─ try: one request
  └─ result:
      ├─ success → CLOSED (normal operation resumed)
      └─ failure → OPEN (or OPEN_EXTENDED if sustained)
```

**Cost Analysis:**

```
Scenario: LLM API provider outage for 2 hours

WITHOUT OPEN_EXTENDED (3-state):
  Probe interval: 30s
  Probes in 2h: 240
  Probe load: 240 requests to degraded service
  Alerts: 240 × "probe failed" (operator alert fatigue)

WITH OPEN_EXTENDED (4-state after 5 min):
  First 5 min: 30s interval → 10 probes
  Next 115 min: 5m interval → 23 probes
  Total probes: 33 (85% reduction)
  Alerts: 1 × "transitioning to OPEN_EXTENDED" + 1 × "recovery detected"
```

- ✅ State transitions
- ✅ Probe interval logic
